Slide 2 • Project Foundations
Introduction, Purpose & Specific Objectives
Problem Context & Purpose
  • The Outpatient Bottleneck: Clinical triage is the time-critical intake process that determines patient acuity. Traditional verbal inquiry by triage staff leads to cognitive fatigue and patient queue delays during peak surges.
  • Two Distinct Modalities: Real-world medical data arrives either as conversational free-text (patient stories) or as structured clinical checklists (nursing forms).
  • Project Purpose: AuraDX delivers a dual-paradigm Clinical Decision Support System (CDSS) providing side-by-side diagnostic verification to assist clinical triage staff in sub-second time.
Specific Measurable Objectives
  • Objective 1 (NLP Accuracy): Design and train a text classification pipeline achieving >90% accuracy (achieved 96.0%) on natural language symptom descriptions using NLTK lemmatization and TF-IDF Logistic Regression.
  • Objective 2 (High-Cardinality ML): Train an ensemble Random Forest classifier predicting across 673 distinct diseases mapped from 377 symptom flags.
  • Objective 3 (160x Compression): Compress the massive ensemble binary from 6.6 GB down to 41.4 MB using Joblib gzip compression (level 3) for fast cold boots.
  • Objective 4 (Live Dashboard): Build and deploy a responsive Flask web interface with animated confidence meters and instant keyword mapping.

Slide 4 • Problem Analysis
Existing System & Critical Limitations
Existing System Overview
  • Manual Verbal Intake: Triage nurses and clinical clerks interview arriving patients and manually enter symptoms into paper forms or legacy EHR portals.
  • Generic Web Checkers: Consumer websites (such as WebMD or rudimentary symptom search bars) rely on basic keyword matching or rigid, hardcoded decision trees.
  • Single-Format Silos: Existing software tools operate strictly on one format: either free-text search OR a closed checkbox questionnaire—never both simultaneously.
  • Rule-Based Rigidity: Keyword matchers cannot interpret colloquial variations or complex descriptions (e.g., 'feeling woozy and spinning' vs 'vertigo').
Critical Limitations
  • No Dual Cross-Validation: Predictions are made in isolation without comparative model verification, drastically increasing false-positive risks.
  • Vocabulary & Syntactic Fragility: Misspellings, synonyms, and narrative noise trigger false alarms or complete lookup failures.
  • Scalability & Queuing Bottlenecks: Manual triage causes severe patient queues during peak outpatient admission hours, increasing nurse cognitive fatigue.
  • Prohibitive Memory Overhead: Scaling multi-class ensembles across 600+ diseases creates 6+ GB uncompressed model binaries, preventing local deployment on clinical workstations.
Slide 5 • Proposed Solution (1/2)
Proposed System & Key Features
Dual-Engine Cross-Validation
  • Unifies an Unstructured NLP Classifier (TF-IDF + Logistic Regression) and a Structured ML Classifier (Random Forest) side-by-side.
  • Allows triage staff to compare narrative-based predictions directly against structured clinical checklist indicators.
High-Cardinality Triage (673 Classes)
  • Engine 2 classifies 673 unique diseases from 377 binary symptom features—scaling far beyond standard 10–20 class academic toy models.
  • Handles complex clinical symptom overlap with an ensemble of 50 decision trees.
160x Model Compression
  • Chunked CSV sampling (`chunksize=25,000`) avoids memory overflow during training.
  • Joblib gzip level 3 compression shrinks the ensemble binary from 6.6 GB down to 41.4 MB, enabling sub-second cold starts.
Glassmorphic Real-Time UI
  • Responsive dark-mode interface with instant keyword suggestion tags.
  • Renders dynamic symptom pills, cleaned text previews, and animated confidence progress bars in under 150 ms.
Slide 6 • Proposed Solution (2/2)
Algorithms Used & Mathematical Application
Algorithm 1: NLP Narrative Classifier
  • Text Sanitation & WordNet Lemmatization: Strips punctuation via regex, converts to lowercase, filters NLTK stopwords, and reduces tokens to lemmas (e.g., "vomiting" → "vomit").
  • TF-IDF Vectorization: Extracts unigram and bigram features (1,2 n-grams) capped at 3,000 dimensions:
    TF-IDF(t, d) = TF(t, d) × log(N / DF(t))
  • Multi-Class Logistic Regression: Employs L2 regularization with L-BFGS solver over 24 disease classes:
    P(y=k|x) = exp(w_k · x) / ∑ exp(w_j · x)
  • Performance: Achieved 96.0% Test Accuracy and 96.0% Macro F1-Score.
Algorithm 2: Structured ML Random Forest
  • Keyword Substring Mapper: Scans free-form user text against a dictionary of 377 verified symptom names, constructing a 1×377 binary vector:
    X_i = 1 if symptom in text else 0
  • Ensemble Random Forest (50 Trees): Aggregates predictions across 50 bootstrap decision trees using the Gini impurity splitting criterion:
    Gini = 1 - ∑ p_i^2
  • Label Encoding & Decoding: Maps 673 string disease targets to integers for training, and inverse-transforms integer predictions back to clinical names during inference.
  • Performance: Achieved 81.6% Test Accuracy and 76.6% Macro Recall.

Slide 11 • Technical Specifications
Technologies Used & System Requirements
Hardware Requirements
  • Processor: Intel Core i3 / AMD Ryzen 3 (Quad Core) min; Intel Core i5 / AMD Ryzen 5 recommended.
  • RAM: 4 GB minimum; 8 GB – 16 GB DDR4 recommended for chunked training.
  • Storage: 1 GB free disk space (SSD recommended).
  • Display: Standard Full HD Monitor (1920×1080).
Software Requirements
  • Programming Language: Python 3.10 / 3.11+
  • Web Framework: Flask 3.0+ (WSGI Local Server)
  • Data Science Libraries: Scikit-Learn, NLTK, Pandas, NumPy
  • Model Persistence: Joblib (gzip compression level 3)
  • Frontend Stack: HTML5, CSS3 Glassmorphism, JavaScript ES6
Operating System & Tools
  • Operating System: Windows 10 / 11 or Linux (Ubuntu 20.04+)
  • Development IDE: Visual Studio Code
  • Version Control: Git & GitHub Repository
  • Data Visualization: Matplotlib, Seaborn (Confusion Matrix Heatmaps)
Database Architecture Used
  • Architecture: Stateless File-Based Machine Learning Storage.
  • Academic Justification: AuraDX is an on-demand inference web engine with no user logins or transactional OLTP records; hence an RDBMS (MySQL/PostgreSQL) is unnecessary.
  • Raw Data: Flat CSV datasets stored in data/.
  • Model Weights: Compressed .joblib binaries stored in saved_models/ (<42 MB total).
